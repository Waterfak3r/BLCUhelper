# BLCUhelper：问题清单与推进路线

> **审查对象**：[`Waterfak3r/BLCUhelper`](https://github.com/Waterfak3r/BLCUhelper/tree/experiment/wechat-mp-tools)  
> **审查分支**：`experiment/wechat-mp-tools`  
> **代码快照**：`1b5322bcbaa18bf3fb712c6f47c5123b54c33010`（2026-10-26）  
> **性质**：静态代码与文档审查后的开发待办，不是线上运行验收报告。  
> **范围**：信源采集、微信公众号桥接、AI 内容处理、质量控制、部署与运维、产品迭代。

## 0. 结论与目标

BLCUhelper 已具备采集、材料入库、AI 处理、公开发布和 Web/RSS/API/MCP 输出的完整工程结构。下一阶段应**优先验证数据是否持续、完整、可信地进入系统，并证明重要校园通知不会被静默遗漏**，而不是继续扩张产品功能。

**阶段性目标**：

1. 53 个预置信源（25 个官网、28 个公众号 RSS）的**配置、实际接入和运行状态可对账**。
2. 微信公众号采集可以连续运行；失败、授权失效、正文缺失时**有明确状态和处理入口**。
3. 校园通知筛选经过真实数据集校准；**重要通知漏选有专门的监测与复核机制**。
4. 形成从「采集 → 核验 → 分析 → 展示 → 人工纠错」的可观测闭环。

> **区分三个概念**：已配置 ≠ 已成功订阅/抓取 ≠ 已核验并公开。产品和后台统计应始终分别显示。

## 1. 问题清单（按优先级）

### P0-01｜公众号 RSS 地址与 Docker 网络不匹配

- **类型**：已确认的配置兼容问题；实际影响取决于部署方式。
- **证据**：`industry/sources.json` 中 28 个 RSS `config.feedUrl` 均使用 `http://127.0.0.1:5200/...`；`docker-compose.wechat-mp.yml` 将公众号采集器作为独立服务运行，并通过服务名 `wechat-mp-tools` 供其他容器访问。
- **风险**：当采集 Worker 运行在独立 Docker 容器时，`127.0.0.1` 指向 Worker 自己，不能访问另一个容器；预置公众号 RSS 可能整体不可用。
- **整改**：
  - [ ] 根据运行形态规范 RSS 地址：Docker 内部使用 `http://wechat-mp-tools:5200`，宿主机进程使用 `http://127.0.0.1:5200`。
  - [ ] 避免把环境专属 Host 永久写死在通用信源种子中；设计部署时地址映射或明确的配置生成步骤。
  - [ ] 只对受信任的采集器 Host 添加 `PRIVATE_FEED_HOSTS` 白名单，**不**为此开启通用私网抓取开关。
  - [ ] 给已入库的 28 个信源提供受控更新路径（后台批量修改/显式迁移）。`scripts/seed.ts` 的 `ON CONFLICT DO NOTHING` **不会**更新已有地址。
- **验收标准**：
  - [ ] 从实际运行的 Worker 容器访问目标公众号 RSS，返回可解析的 XML。
  - [ ] 主站后台手动试抓能记录明确的成功/失败状态。
  - [ ] 重新部署不会把修复后的地址覆盖成另一种环境的地址。
- **相关文件**：`industry/sources.json`、`docker-compose.wechat-mp.yml`、`scripts/seed.ts`、`packages/backend/src/sources/rss.ts`。

### P0-02｜预置信源与采集器实际订阅没有对账

- **类型**：已确认的架构缺口，在线是否发生空订阅需运行时验证。
- **证据**：`industry/sources.json` 声明 28 个默认启用的 RSS 源；`scripts/setup-wechat-mp-tools.ts` 负责检出固定上游版本、应用补丁和初始化安全配置，但**不负责建立全部公众号订阅**。
- **风险**：即使 RSS 接口可访问，也可能返回合法空源；主站看到「抓取成功」却没有任何文章，造成隐形覆盖缺口。
- **整改**：
  - [ ] 引入「预期信源 ↔ 采集器已启用订阅」对账。
  - [ ] 在后台区分：**未配置**、**待身份核验**、**未订阅**、**订阅中**、**最近采集成功**、**异常/停更待确认**。
  - [ ] 为每个源记录最近有效采集时间、最近文章时间、近 7 天新增数量、最近错误原因。
  - [ ] 未确认身份或未实际建立订阅的公众号先不要按「正常覆盖」对外展示。
  - [ ] 对账警报与采集器自身进程健康分开，避免「服务健康 = 信源完整」的误判。
- **验收标准**：
  - [ ] 可以输出 28 个公众号逐个对账表，且能指出缺少实际订阅的账号。
  - [ ] 模拟一个从未订阅的 RSS 账号，不被标记为已正常覆盖。
  - [ ] 对「无新文章」与「采集失败」有不同状态；无法判断时明确标记为「待核实」。
- **相关文件**：`industry/sources.json`、`scripts/setup-wechat-mp-tools.ts`、`packages/backend/src/sources/health.ts`、`scripts/wechat-mp-watchdog.py`。

### P1-01｜公众号身份与信源等级需要逐个核验

- **类型**：风险待验证。
- **证据**：28 个公众号 RSS 在种子中预分为 `T1`（20 个）与 `T1_5`（8 个），并关联校园主体；配置存在不等于官方身份全部完成核验。
- **风险**：重名公众号或非官方账号被视作官方来源；可能影响 AI 评分和学生信任。
- **整改**：
  - [ ] 逐账号建立核验档案：公众号名称、稳定账号标识、官方证明链接、所属单位、最后核验时间。
  - [ ] T1/T1.5 等级必须有可追溯的判断依据，未核验者设为待审核而非默认已确认。
  - [ ] 账号改名、停更、转移时重新核验。
- **验收标准**：28 个源均能提供身份结论及证据；未通过核验的源不被当作已验证官方源自动发布。
- **相关文件**：`industry/sources.json`、`docs/sources.md`。

### P1-02｜图片型公众号通知的正文与行动信息缺失

- **类型**：已在小样本中观察到的问题；覆盖比例不能直接外推。
- **证据**：部署文档中的「北语青年」试采：8 篇下载成功，但仅 4 篇具有可用文字，另外 4 篇正文只有极少文字或主要由图片构成，被保留为 `pending`。
- **风险**：海报上的报名条件、日期、二维码、地点、附件说明等可能无法进入 AI 流水线。
- **整改**：
  - [ ] 给材料增加清晰的内容完整性/核验状态：例如 `complete`、`image_dependent`、`attachment_dependent`、`verification_required`（命名可按现有模型调整）。
  - [ ] 先建立人工审校入口，再评估低成本视觉识别或 OCR 作为**提取候选**；不可把提取结果未经校对直接视为事实。
  - [ ] 图片、PDF、附件的提取结果必须保留原始证据关联；不能凭标题补造办理条件或链接。
  - [ ] 将此类材料纳入「待核验」工作台和健康统计。
- **验收标准**：抽取真实的图片型通知样本，能够明确显示未解析的字段；人工核验前不输出猜测出的截止日期和申请方式。
- **相关文件**：`packages/backend/src/content/extract.ts`、`packages/backend/src/content/attachments.ts`、`docs/deploy.md`。

### P1-03｜AI 精选逻辑尚未完成校园数据校准

- **类型**：已确认的上线前质量缺口。
- **证据**：当前 `T1=60`、`T1_5=65`、`T2=76`、`understandFloor=50`，继承自 AIHOT；README/选择文档明确要求校园真实样本标注与效果验证。
- **风险**：普通资讯场景的「控制噪声」优先级，与校园通知场景的「不要漏掉必须办理的事项」不完全一致。
- **整改**：
  - [ ] 优先人工核验约 30 条真实材料以检查完整流水线，再整理约 100 条金标样本（建议 60 development / 40 holdout）。
  - [ ] 单独覆盖教务考试、奖助评优、升学就业、国际交流、志愿活动，以及难判断的跨学院资格通知。
  - [ ] 用 `node scripts/eval-selection.ts --check-only --gold ...` 先做离线样本检查。
  - [ ] 评估预筛、双评分及最终精选结果；**单列关键行动通知的漏报数**，不要仅看总体 F1。
  - [ ] 设计「完整通知池」与「AI 精选层」的不同准入原则：重要、可信但分数低的校园事项不应被静默吞掉。
- **验收标准**：
  - [ ] 有固定 holdout 样本和可重现的评测报告。
  - [ ] 按文档目标报告召回率、精确率、有效输出覆盖率及分子/分母；重点审查所有「必须办理」漏报。
  - [ ] 精选阈值的改动有数据依据，而非凭观感调整。
- **相关文件**：`industry/selection.ts`、`industry/prompts/`、`docs/selection.md`、`scripts/eval-selection.ts`。

### P1-04｜实验分支及 Python 组件缺少完整自动化验收

- **类型**：已确认的 CI 覆盖缺口。
- **证据**：`.github/workflows/check.yml` 的 `push` 仅监听 `main`；当前试验涉及的 `wechat-mp-tools` 上游补丁、Python 测试与 Watchdog 测试没有纳入该工作流的完整验证。
- **风险**：实验分支修改后不会因普通 push 自动验证；上游补丁可能不再适用，或者 Python 组件回归未被发现。
- **整改**：
  - [ ] 让实验分支至少可以手动触发整套 CI，或按需要配置分支触发条件。
  - [ ] 新增独立 Job：检出固定上游 commit → 执行 `scripts/setup-wechat-mp-tools.ts` → 确认补丁可应用 → 运行上游相关 Python 测试。
  - [ ] 运行 `python3 -m unittest discover ...` 或仓库实际指定的 Python 测试命令，覆盖 `tests/test_wechat_mp_watchdog.py`。
  - [ ] 增加一个从 RSS 到主站材料入库的集成测试（用本地合成源，严禁依赖真实微信账号）。
- **验收标准**：实验分支的新提交可自动/手动得到明确的 Typecheck、构建、Node 测试、Python 测试、补丁验证结论。
- **相关文件**：`.github/workflows/check.yml`、`deploy/wechat-mp-tools.patch`、`tests/test_wechat_mp_watchdog.py`。

### P1-05｜公众号服务长时间无人值守能力尚未验证

- **类型**：待运行验证的运维风险。
- **证据**：Watchdog 已实现 10 分钟巡检、故障分类、每小时受控重启、失效授权二维码邮件及状态持久化；但文档说明未完成长期自动续期与全站稳定运行观察。
- **风险**：微信上游风控、账号失效、验证码、订阅排程停摆均可能导致数据断流。
- **整改**：
  - [ ] 按实际部署方式连续观测多轮采集、重启和授权恢复。
  - [ ] 验证人工停止不会被自动拉起；验证码不能被自动绕过；失效二维码不再投递。
  - [ ] 建立运行指标：成功采集轮次、鉴权失败次数、异常平均恢复时间、待核验队列长度。
  - [ ] 区分「账号本地缓存 active」与「微信接口真实可用」。
- **验收标准**：留存覆盖工作日和周末的完整运行记录；至少演练一次认证失效、一次排程异常、一次人工停机。
- **相关文件**：`scripts/wechat-mp-watchdog.py`、`deploy/systemd/`、`docs/deploy.md`。

### P1-06｜管理面安全与上游使用许可

- **类型**：部署安全约束 + 上线前合规问题。
- **证据**：公众号采集器上游管理界面没有全局鉴权；当前 Docker 方案只监听宿主机回环地址。上游许可文本与 README 的用途限制描述存在不一致。
- **风险**：误映射公网端口暴露管理接口和会话；公开/商业部署可能面临许可争议。抓到正文不等于取得全文再分发授权。
- **整改**：
  - [ ] 坚持管理端口仅本机访问；远程维护优先 SSH 端口转发。
  - [ ] 审查同 Docker 网络中其他服务访问采集器管理端点的权限；RSS Token 不作为管理后台鉴权。
  - [ ] 在对公众提供服务前澄清上游许可与使用限制。
  - [ ] 保持公众号全文默认不公开，仅提供经过校验的摘要、来源及原文链接。
- **验收标准**：公网无法访问采集管理接口；第三方代码与内容再利用边界形成书面记录。

### P2-01｜模型分工与成本尚未量化

- **类型**：优化空间，非已确认故障。
- **证据**：`site/models.ts` 预置多个模型，但 `DEFAULTS` 为空；实际路由由环境变量/后台设置决定。现有底层已具备付费回执、缓存复用与预算限额。
- **风险**：完整 AI 处理链每篇可能产生多次模型请求；强模型用于所有阶段容易造成预算压力。
- **整改**：
  - [ ] 先按阶段记录 Token、价格、耗时、错误率、人工纠错率。
  - [ ] 仅在金标验证后，为预筛、分类、摘要、评分、归组分别选择适当的低成本模型。
  - [ ] 保留双评分/必要证据核验作为对照基线，优先优化重复调用和无意义重试。
  - [ ] 为不同供应商设计可观察的失败与降级策略，不能把失败当作已完成。
- **验收标准**：有按阶段的成本及质量报表；优化前后能比较成本、召回率、输出完整率和错误率。
- **相关文件**：`site/models.ts`、`packages/backend/src/providers/receipts.ts`、`packages/backend/src/editorial/`。

### P2-02｜缺少面向学生行动的结构化信息

- **类型**：下一阶段产品能力，不属于本期必须立即实现的缺陷。
- **证据**：当前范围明确不引入单独 `deadline` 字段、日历及提醒。
- **价值**：相比仅提供摘要，明确的「谁需要办理、做什么、何时截止、在哪里操作」更贴合校园需求。
- **建议（后置）**：
  - [ ] 在有质量基线后，讨论增加 `actionType`、`deadlineAt`、`eligibleAudience`、`actionUrl`、`verificationState` 等结构化字段。
  - [ ] 明确区分发布日期、活动日期、截止日期，必须有原文证据才能填充。
  - [ ] 先实现关注学院与类别，再评估截止日期提醒或日历。
- **验收标准**：结构化字段来自可回溯证据；不把文章发布日期当作截止日期。

## 2. 分阶段推进路线

### 阶段 A｜先让采集和部署可信（最高优先级）

**范围**：P0-01、P0-02、P1-01、P1-04 的采集部分。

- [ ] 修复 Docker/宿主机 RSS 地址差异，明确旧数据库信源更新方案。
- [ ] 建立 28 个公众号的订阅对账与身份核验清单。
- [ ] 检查每个公众号 RSS 的实际可用性及最近有效文章。
- [ ] 给采集器补丁和 RSS 入库链路加自动化测试。
- [ ] 后台真实展示信源的「已配置 / 已订阅 / 已采集 / 已核验」状态。

**交付物**：一份可复现的部署配置、一张 53 源状态对账表、一组持续通过的基础测试。

**完成定义（DoD）**：任意预置信源的异常都能被定位；系统不再把一个合法的空 RSS 误认为覆盖已经达标。

### 阶段 B｜解决正文完整性与 AI 漏报（核心价值）

**范围**：P1-02、P1-03、P2-01 的测量部分。

- [ ] 统计官网/公众号正文完整度，专项整理图片和附件型通知。
- [ ] 提供需要人工核验的内容工作台与证据链。
- [ ] 建立真实校园通知金标集并运行离线评测。
- [ ] 评估预筛、评分和最终精选对「必须办理通知」的漏报。
- [ ] 区分完整通知池与精选推荐层，修正静默丢弃路径。
- [ ] 采集每阶段模型成本、延迟和失败数据，为后续路由调整提供基线。

**交付物**：正文完整性报告、校园精选评测报告、错误与漏报案例库。

**完成定义（DoD）**：能够用真实样本说明为什么某条通知被收录、待审核、精选或未精选，并能追溯证据和失败原因。

### 阶段 C｜验证长期运行并小范围试用

**范围**：P1-05、P1-06 及产品体验验证。

- [ ] 完成持续采集观察和故障演练。
- [ ] 检查管理接口访问边界、凭据隔离和上游许可。
- [ ] 邀请小范围真实学生试用搜索、学院筛选和通知阅读。
- [ ] 重点记录：漏通知、来源不符、摘要不准、日期不明、链接失效。
- [ ] 根据真实使用反馈决定是否进入行动结构化功能。

**交付物**：运行稳定性记录、上线约束清单、试用反馈与下一阶段需求排序。

**完成定义（DoD）**：已经明确产品能覆盖什么、不能保证什么；能连续运行并在缺口出现时及时发现和处理。

### 阶段 D｜逐步实现「阅读 → 行动」

**前置条件**：阶段 B/C 的准确性和稳定性得到证据支持。

- [ ] 提取「适用人群、办理事项、截止时间、办理入口」等行动字段。
- [ ] 允许用户关注学院、身份标签、信息类型。
- [ ] 在具备可信截止日期后，考虑提醒、日历或待办集成。
- [ ] 优先强化核心校园信息服务，不急于扩张到社交、论坛等非核心方向。

**完成定义（DoD）**：学生不仅能看到信息，还能可靠判断「这条通知和我是否有关、现在需要做什么」。

## 3. 建议的执行顺序（精简版）

| 顺序 | 任务 | 优先级 | 完成后应看到什么 |
|---:|---|---|---|
| 1 | 修复 RSS Docker 网络地址及已有信源配置 | P0 | Worker 真正抓到公众号 RSS |
| 2 | 建立 28 个公众号订阅及身份对账 | P0 | 每个源都有准确的运行/核验状态 |
| 3 | 补公众号组件与分支 CI | P1 | 修改可自动发现回归 |

## 4. 不建议现在做的事

- **不建议**把「53 个已配置源」宣传成「53 个已覆盖源」。
- **不建议**直接启用所有新公众号的自动公开与高可信等级，而跳过身份、内容完整性核验。
- **不建议**为了节约模型费用直接砍掉全部复核环节；应先测量真实准确率和每步成本。
- **不建议**在没有可靠正文和校准数据的情况下做自动截止日期提醒，以免传播错误办理信息。
- **不建议**当前阶段同时扩展聊天机器人、论坛、社交等大型功能。
- **不建议**把采集服务的进程存活/HTTP 200 等同于所有公众号通知已成功采集。
